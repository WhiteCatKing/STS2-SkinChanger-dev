# 两边交接（云 ↔ 白猫）

两边各有自己的 AI 在改同一个仓库。**一边要另一边知道、接手或合并的东西，都写成交接文件，放在这个目录里，跟代码一起推上去。**不再靠聊天转发长文。

和 `STS2-SkinChanger_修改件/docs/refactor/` 的区别：`docs/refactor/` 是每个任务自己的技术记录（过程、测量、复核轮次）；这里是两边之间的交接，只写对方需要知道和需要做的。

## 什么时候写

- 推一条要对方合并的分支时（云推 `merge/...`；白猫更新 `main`，并且影响到对方正在做的事）。
- 把问题转给对方修时。
- 回复对方的交接时。

## 放哪里、怎么命名

- 文件名：`docs/handoff/YYYY-MM-DD_<写的一方>_<主题>.md`，写的一方写 `云` 或 `白猫`。例：`2026-11-26_云_1.0.41.23性能与稳定性.md`。
- 交接文件和它说的代码放在**同一个分支、同一次推送**里。只补文档时，可以单独一个提交。
- 每写一份，在本文末的索引表加一行；对方处理完，把"状态"改掉。

## 必须有的几节

照这个顺序写，没有内容的节写"无"，不要删掉：

1. **一句话**：做了什么，对方要做什么。给人看，不写代码名词。
2. **分支与提交**：基于对方的哪个提交；本分支的提交列表（短哈希 + 一句话）；内测版本号。
3. **改动须知**：会改变对方以后写代码方式的东西，例如新的统一入口、新的规矩、新增的门禁项、改了对方的哪段代码及原因。每条都写"以后怎么做"。
4. **验证**：门禁结果（总数、通过、失败，正式版和测试版两种引用各自的结果）；实机测试里哪些实测通过，哪些只有离线测试通过；测试环境的特殊情况（例如临时停用了哪些 Mod）。
5. **归对方的问题**：逐条编号。每条写清位置（文件、函数）、正常玩家怎么碰到、后果、建议修法和改动量、分档（阻塞 / 建议尽快 / 以后再修）。已经顺手修掉的对方代码也列在这里，写"已修，在哪个提交"，让对方知道自己的代码被改了。
6. **未完成、待确认**。
7. **需要对方答复的问题**：每条都能直接回答"是 / 否 / 选哪个"。

## 回复

- 收到交接后，在自己下一次推送里写一份回复：`YYYY-MM-DD_<写的一方>_回复_<原文件的主题>.md`。按原文件的编号逐条写：已修（哪个提交）/ 不修（理由）/ 待定（缺什么）。
- **不改对方写的交接文件**，只新写文件。索引表的"状态"一栏例外，双方都可以改。

## 写法

- 用中文。先说结论，再说原因；一句话只说一件事。
- 路径写仓库内的相对路径。不写本机绝对路径、账号、邮箱、Steam ID 这类个人信息；日志只摘相关的几行。
- "一句话"那一节写给人看；后面的细节写给对方的 AI 看，文件名、函数名、测试名都写全。
- 须知和问题清单要写全，排查过程不写（过程放 `docs/refactor/`）。
- 拿不准的地方，写出怎么确认、下一步做什么。
