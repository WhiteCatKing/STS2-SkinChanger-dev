# 联机进商店黑屏：自定义角色商店场景 `InvalidCastException`——根因与修复建议

> 日期 2026-11-15。反馈者环境：游戏 `v0.113.1`（PublicBeta），皮肤切换器工坊版（启动日志 `内测版本 1.0.32.0`），BaseLib `v3.4.8`，RitsuLib `0.6.13`，魔法少女/天音 `MaidenSuccubus 0.1.0`（工坊 3811028356）。
> 附带：
> - `godot_日志摘录_商店黑屏_20261115.txt`：出错那局的日志原文摘录（原文件已被游戏日志轮换删除，见文件开头说明；Steam ID 已脱敏）。
> - `MultiplayerMerchant_自定义角色商店场景回退原逻辑.patch`：参考补丁，基于 `origin/main` = `52fe010`，`git apply --check` 通过。

- 状态：**未解决**

## 1. 现象

- 4 人联机（客户端，非房主），队伍里有魔法少女（天音）角色，本机也是天音。
- 大家走进商店 `(4,2)`：**只有装了皮肤切换器的本机黑屏**，其他三位玩家商店正常，还在买东西（日志里能看到他们的 `MerchantEntryPurchasedMessage`）。
- 随后房主断开连接，本机被退回主菜单。

## 2. 根因

### 2.1 直接原因

`Core/MultiplayerRoomAppearancePatches.cs` 中的 `MultiplayerMerchantPlayerVisualIsolationPatch`：

- 用 `Priority.First` 的 Prefix 接管 `NMerchantRoom.AfterRoomIsLoaded`，人数大于 1 时自己重写一遍建人物形象的循环，并 `return false` 跳过游戏原逻辑。
- 循环里固定写死：

```csharp
var visual = PreloadManager.Cache
    .GetScene(player.Character.MerchantAnimPath)
    .Instantiate<NMerchantCharacter>(PackedScene.GenEditState.Disabled);
```

天音的商店场景根节点是普通的 `Godot.Node2D`，不是 `NMerchantCharacter`，于是：

```
ERROR: System.InvalidCastException: Unable to cast object of type 'Godot.Node2D' to type 'MegaCrit.Sts2.Core.Nodes.Screens.Shops.NMerchantCharacter'.
   at STS2SkinChanger.Core.MultiplayerMerchantPlayerVisualIsolationPatch.Prefix(...)
   at MegaCrit.Sts2.Core.Nodes.Rooms.NMerchantRoom.AfterRoomIsLoaded_Patch2(NMerchantRoom this)
   at MegaCrit.Sts2.Core.Nodes.Rooms.NMerchantRoom._Ready_Patch5(NMerchantRoom this)
```

异常从 `_Ready` 一路抛出，`AfterRoomIsLoaded` 没有完成，房间处于半初始化状态。接着 `NMerchantRoom.OnActiveScreenUpdated()` 空引用，`MoveToMapCoordAction ... completed with exception` → 黑屏（日志摘录第 2、3 节）。

### 2.2 为什么原版流程不出错（推测，未反编译确认）

- 同一时间另外三位玩家（没装皮肤切换器）走的是游戏原流程，商店正常。可见游戏原流程（加上其他 Mod 的补丁）能处理根节点为 `Node2D` 的自定义角色商店场景。
- BaseLib 启动时会打 `[BaseLib] Created node factory for NMerchantCharacter.`，`BaseLib.dll` 里也有 `NodeFactory`、`ConvertScene`、`CustomMerchantAnimPath` 等字符串。推测是 BaseLib 在原流程里把自定义角色的 `Node2D` 场景转换成了 `NMerchantCharacter`。
- 本补丁以 `Priority.First` + `return false` 直接接管，并用 `Instantiate<NMerchantCharacter>()` 强转，**绕过了这层转换**。

### 2.3 补充

- 这个 Prefix 只判断 `____players.Count <= 1`。反馈者配置里 `MultiplayerSkinSyncEnabled=false`、`LoadOtherPlayersCustomSkins=false`，补丁仍然生效。也就是说，关掉联机皮肤同步也绕不开这个问题，只能整个禁用皮肤切换器。
- 本机自己就是天音，按代码会先把本机移到第 0 位，所以很可能第一次 `Instantiate` 就抛异常了，还没往 `____characterContainer` 里加任何节点。

## 3. 修复（参考补丁，只改 `Core/MultiplayerRoomAppearancePatches.cs`，+36 / −11）

思路：**先把所有玩家的场景实例化并检查类型，全部通过再摆放；只要有一个不是 `NMerchantCharacter`，就释放已建好的节点，`return true` 交还给游戏原流程。**

- 实例化仍在每位玩家各自的 `BeginPlayerRuntimeScope` / `RemoteRoomSceneLease` 作用域内进行，原有的「按玩家隔离皮肤」逻辑不变。
- 改用非泛型的 `Instantiate(...)` 加 `is NMerchantCharacter` 判断，不再强转。
- 回退时打一条 `[商人] <角色> 的商店场景根节点是 <类型>，不是 NMerchantCharacter；本房间改走游戏原逻辑。`。
- 代价：只要队伍里有这类自定义角色，该商店房间就不做按玩家的皮肤隔离（同角色的其他玩家可能显示本机选的皮肤），但不会再黑屏。
- 玩家顺序的调整（本机放到第 0 位）保留在回退之前。上面注释写的是「镜像游戏的循环」，游戏原逻辑本来也会这样排序。如果原版并不这样排序，回退前需要先恢复原顺序。

更彻底的做法是：遇到非 `NMerchantCharacter` 根节点时，复用 BaseLib 的节点工厂把它转换后继续走隔离逻辑。但这需要确认 BaseLib 的公开接口，本次没有做。
