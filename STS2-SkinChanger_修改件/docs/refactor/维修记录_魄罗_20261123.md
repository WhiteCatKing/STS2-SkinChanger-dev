## 一、这次改了什么（三处）

1. **实例化工厂**（`STS2SkinChanger/Core/PoroVariantBridge.cs`）
   探测结果从「拿着 `GDScript` 资源直接 `Call("data_for")`」改成 `Discovery(Pack, ScriptPath, Options)` 记录包与脚本路径，取骨架时用 `GetFactory(discovery)` 现取现用：`ResourceLoader.Load<GDScript>(...)` → `.New()` → 在实例上 `Call("data_for", skinId)`。原来对脚本资源本身调用实例方法拿不到骨骼，所以选了也没变化。

2. **预览选项缓存**（同文件）
   去掉一次性 `_discovered` 标志与 `Reset()`，改成按 `SkinService.Catalog` 实例缓存：目录对象换了才重新探测（`ReferenceEquals(catalog, _catalog)`）。这样换皮、重新扫描目录后选项不会凭空消失。

3. **随从私有资源包**（同文件 + `Core/SkinService.cs` + `Ui/OstyModelPreviewControls.cs`）
   探测改从提供者的 **PCK 文件**里读（`catalog.GetProviderResourcePackPaths(provider)` + `PckArchive.Open`，按 `res://<provider>/scripts/spine_factory.gd` 与 `spine42/*.spine-json` 判断），不再依赖磁盘解包目录；随从判定用游戏结构 `creature.Monster is Osty && creature.PetOwner is { } owner && LocalContext.IsMe(owner)`，刷新遍历 `NCombatRoom.Instance.CreatureNodes` 并取 `owner.Visuals`；预览刷新键纳入魄罗选项，魄罗选中时跳过普通奥斯提场景，改选别的随从时清除魄罗选择。
   **战斗里只更新本机玩家的奥斯提**：`IsCompanion` 里 `LocalContext.IsMe(owner)` 把范围锁在自己身上，所以多人的其他玩家随从、本体和预览小人都不再被替换（此前只判 `PetOwner != null && Monster is Osty`，会把别人的随从/自己的本体一起改掉）。
   同时新增 `PoroVariantBridge.CompanionFiles(...)` 供测试直接校验包里两档随从资源。

## 三、门禁排查记录

1. **`--test-game-branch` 假阳性**（**已由 Codex 修好**）
   `ProviderAssemblyCompatibility.AuditGameReferences` 原先拿 Cecil 的成员返回类型字符串 `System.Void modreq(System.Runtime.CompilerServices.IsExternalInit)` 去和反射的 `ReturnType.FullName`（只有 `System.Void`）比较，永远不相等。凡 `init` 属性的 setter 全部误报。旧安装（未更新比对的那份）能稳定复现这三条：`AncientDialogueSet::set_AgnosticDialogues / set_CharacterDialogues / set_FirstVisitEverDialogue`（由 `Core/HildeAncientDialogueCompat.cs` 的对象初始化器引用）。
   反射实测（`[Reflection.Assembly]::LoadFrom('C:\sts2refs\stable\sts2.dll')`）：三个 setter 都存在，`ReturnParameter.GetRequiredCustomModifiers()` 含 `IsExternalInit`。
   修法：`ProviderAssemblyCompatibility.Rules.cs` 新增 `RuntimeParameterTypeName(ParameterInfo)`，把 `modreq(...)` 拼回去再比对。新比对下两个分支都 `Branch ABI passed: a5742661… / 9d417b39…`、`zero rewritten/unresolved references`；旧安装则复现上述 3 条误报——两边对照可确认是比对缺 `modreq`，不是产物缺成员。

2. **`tools/check-dual-branch.ps1` 的两处构建都不带 `--no-incremental`**
   在别的引用构建过之后，产品重编会退化成 no-op，脚本核验的其实是上一份产物——这正是此前门禁「能过」、这次真编后才暴露假阳性的原因。建议给两个 `dotnet build` 都加 `--no-incremental`。

3. **`C:\sts2refs\stable` 缺 `Sentry.Godot.dll`**（环境问题，已修）
   该目录只有 `Sentry.dll 831,488 B`（6.7.0.0）。任何用 stable 引用的测试进程都会在 `<Module>` 初始化时抛 `FileNotFoundException: Could not load file or assembly 'Sentry.Godot, Version=1.0.0.0…'`（`EXIT=-532462766`）。已从游戏目录复制 `Sentry.Godot.dll 59,392 B` + `Sentry.Godot.xml 46,275 B` 进去；另需清 `tests\STS2SkinChanger.RuntimeTests` 与 `tests\STS2SkinChanger.ScriptPathFixture` 的 `obj\Release`/`bin\Release`，否则会继承旧的引用构建。

4. **两个配置产物尺寸不同**：Release 3,773,440 B vs ReleaseBeta 3,978,752 B。`STS2SkinChanger.csproj` 只有一个 `PropertyGroup`，没有 `ReleaseBeta` 专属属性/常量，属于自定义配置按未优化默认编译。发布只用 Release（正式引用）那一份；文档里「两处同尺寸」的旧说法应更正。
