# 切换时提权选包提速

基线 `7fd616c`，分支 `perf/pack-select-20261124`。11 月 23 日实机日志显示，已挂载的 20–22 个包只需跳过或重检其中一包，但「选包」仍花 47.5–51.6 ms。下面的离线基准只计 `MountSelectedLargeRuntimeProviderPacks` 的选包阶段。

## 定位

从本机测试版游戏 PCK、`mods`、工坊目录和切换器当前保存的选择重放旧算法。扫描得到 197 份 PCK 描述，目录有 127 个分组、352 个选项，当前离线输入产生 13 个入选包。这与实机记录中的候选包数不同。每组先预热一次，再取 24 轮均值，并比较新旧的三个结果集合。

| 原选包阶段 | 平均耗时 |
| --- | ---: |
| 读取有效选择与定位选项 | 0.063 ms |
| 判定是否需要完整运行包 | 1.001 ms |
| 判定是否仅随从使用 | 0.439 ms |
| 查询提供者包路径，含存在检查 | **50.595 ms** |
| 规范化路径、查询体积并过滤 | 1.866 ms |
| 生成入选、随从及拟提权集合 | 0.032 ms |
| **总计** | **54.021 ms** |

路径查询的旧谓词在逐个检查 `_cosmeticIndexes` 时反复调用 `ResolveVisualProviderId`。那次解析会重新遍历整个目录的选项，形成「每位提供者 × 每份索引 × 全部选项」的重复工作。把解析移到索引循环外后，即使每轮都重查来源，整个选包也降到 5.138 ms。有效选择和来源检查都已预热时为 2.693 ms。两项数据均来自离线基准。

## 改动与失效

- `SkinService.MountSelectedLargeRuntimeProviderPacks` 从 `SkinCatalog.SelectProviderPacks` 直接取得原有的入选、仅随从和拟提权集合。每组只读取一次有效选择，每位入选提供者在这一轮只查一次完整包条件、随从条件及路径。规范路径挂载、安全过滤、拦截回退继续走原流程。
- `SkinCatalog.GetIndexedProviderResourcePackPaths` 先解析一次提供者 ID，再逐索引匹配。选包汇总保持目录顺序和原有路径比较规则。共享包只在所有命中都属于随从时被标为仅随从。完整运行包仍可低于 64 MiB，其余候选按原体积门槛判断。每次调用单独按受影响分组生成拟提权集合。
- 文件状态缓存与目录实例同寿命，按索引给出的源路径记录绝对路径、大小及 UTC 修改时间，也记录缺失。容量为 512 项，单调时钟到期两秒后再使用该路径会立即重查。有效选择变化时清空观测。重新扫描重建目录会自然取得空缓存，会话索引增删也会主动清空。时间变化但大小仍符合门槛时，重新取得的入选结果可以相同。
- 保留现有的「提权包预检明细」一行。分段计时只留在离线基准中。

## 验证

- `pack-selection-cache` 在四个提供包的干净夹具上逐项对比原算法。覆盖仅随从、随从与主人共享、小而必须完整挂载、小于门槛和恰好达到门槛。另测受影响组变化、选择变化、实际文件时间和大小变化，以及新目录实例下的同路径重查。
- 正式版和测试版构建通过。双引用门禁 **38 项，34 PASS、4 PASS+EXT、0 失败**。两个无参 RuntimeTests 的末行均为 `Workshop policy tests passed.`。受保护角色实包检查由 Claude 按任务分工复跑。
- 门禁输出在 `%TEMP%/sts2-gates-gpt-pack-select`，汇总为 `%TEMP%/sts2-gates-gpt-pack-select.log`。原始测量和同轮对照分别在 `%TEMP%/sts2-pkselect-bench.log`、`%TEMP%/sts2-pkselect-bench-optimized.log`。可用测试版 RuntimeTests 执行 `--bench-pack-selection <游戏PCK> <切换器配置> <mods目录> [工坊目录]` 复跑。基准只读目录。

## 实机验收

1. 用与 11 月 23 日相同的 Mod 和选择开游戏。先等选中包挂完，再切普通资源皮肤与带代码的皮肤。每组切换三次，收集 `[性能] 提权包预检明细`。
2. 对比 `已挂跳过` 接近 `选中包` 的行。预期「选包」进入个位数毫秒。首次的安全过滤和写包耗时仍单独记录。
3. 换回原选择，并检查一次只有随从选中该包、一次主人也引用同一包。核对显示和拟提权数量与旧流程一致。少量 Mod 的干净环境再做一次。
