# 皮肤切换器 · 修复与测试流程（给 AI）

> 用法：与 [维护规矩](maintenance-rules.md) 一起读；`AGENTS.md` 只放摘要与链接，细节以这两份为准。
> 《规矩》写的是**哪些修复不能丢、哪些坑踩过**；本文写的是**一个问题从报上来到交付，每一步怎么做、做到什么程度才算完**。
> 这套流程来自 11-14 到 11-21 三轮修复的实际做法，已经简化过。每一步都有理由，不要跳步。

## 总原则（四条）

1. **先查清原因，再改代码。** 原因说不清，就交"结论 + 证据 + 待确认项"，不要先动手。
2. **一次只解决一个问题。** 一件事改完、测完，再做下一件。顺手发现的问题记下来，另开一单。
3. **离线全绿 ≠ 实机正常。** 画面、点击、加载顺序这类问题，必须有人进游戏确认。AI 负责写清楚测试步骤，人负责点。
4. **证据要能复现。** 结论里写文件、函数、日志行号、包的版本，别人照着能找到同样的东西。

---

## 第 1 步：收问题

先把这几样要齐，缺了就向报告人要，不要靠猜：

| 要什么 | 在哪里 |
|---|---|
| 游戏日志 | `%APPDATA%\SlayTheSpire2\logs\` 里对应那次运行的 `godot*.log`（每次启动会把上一份改名归档，**按时间找对是哪一份**） |
| 崩溃诊断（如果崩了） | `%APPDATA%\SlayTheSpire2\Gurio.SkinChanger\diagnostics\` |
| 开着哪些 Mod | 截图或列表；重点问**最近新装、更新了什么** |
| 游戏版本 | 正式版还是测试版（两者的资源路径和方法签名可能不同） |
| 复现步骤和截图 | 选了什么皮肤、在哪个界面、做了什么操作 |

## 第 2 步：定位（只读）

按下面的顺序来，前一步能定位就不往后走：

1. **读日志。** 按精确关键词分别搜（皮肤 ID、`[ERROR]`、`Exception`、`Loading Godot PCK`、`已隔离皮肤提供者` 等），**不要只看前几十条匹配**：清单类的行会把真正的报错挤出视野。
2. **确认日志属于哪个构建。** 不要只看文件时间，要用日志里能区分构建的特征来判断，比如版本号、补丁计数"保留 N 个原作者行为补丁"。
3. **静态查第三方包。** 用读元数据的方式（`System.Reflection.Metadata`）看它的 DLL 补丁了什么、引用了什么；列出它 PCK 里的路径，再和游戏本体的 PCK 比对有没有同名文件。**不要加载或执行第三方 DLL。**
4. **分清新老问题：做 A/B。** 把上一版 DLL 换回去，让测试的人只看两三个点。上一版也有的，就是老问题；上一版正常的，就是新改动引起的。部署时只保留最近两版就够了。
5. **写定位结论。** 内容包括：根因（一句话），证据（文件:行、日志行号），是不是切换器的问题，影响范围（正式版/测试版、哪些包）。

> 结论是"第三方包自己的问题"也完全可以接受（例如包和当前游戏版本不配、包里有和游戏本体同名的文件、两个 Mod 程序集同名）。这种情况写清楚，给出玩家能自己做的处理办法；**不要为了兜底去侵入式地修别人的包**。

## 第 3 步：修改

- **只改和这个问题相关的文件**，不顺手重构，不批量改格式，换行保持 LF。
- **改在共用的地方，不写特例。** 同一个判断在两处各写一份，迟早会不一致（卡图匹配就出过这种事）。要特殊处理某个包时，用显式的合同或表登记，**不要按工坊标题、包名猜**。
- **游戏路径不写死。** 按实际加载的游戏包去解析，正式版和测试版都要能找到。
- **原版资源路径不许被全局改写。** 提供者的资源一律走私有路径；必须有例外时，登记清楚理由和对应的测试。
- **拦第三方补丁要精确到具体成员**（例：只拦 `CardModel.PortraitPath`），拦宽了会误伤（例：#259 一度连带破坏了日奈的图鉴头像）。
- **UI 注入：Godot 节点先入树，再调用依赖 `_Ready` 的方法。** 注入代码自己抛的异常，不能打断同一回调链上其他 Mod 的逻辑。
- **碰到产品取舍就停下来问维护者**（保留不保留、上限多少、要不要禁用某个包），不要自己拍板。

## 第 4 步：离线验证（门禁，全部通过才算完）

| # | 检查 | 通过标准 |
|---|---|---|
| 1 | 正式版引用构建 | 0 错误（`-p:GameAssemblyDir=<正式版>\data_sts2_windows_x86_64`） |
| 2 | 测试版引用构建 | 0 错误 |
| 3 | LogicTests | 全部通过 |
| 4 | **完整无参数** RuntimeTests | 跑到最后一行 `Workshop policy tests passed.`（运行前先 `SetErrorMode(3)`） |
| 5 | 受保护角色真实包回归 `tools/check-protected-characters.ps1` | 改到十字军、贞德、选人、共享加载入口时必跑，全部通过 |
| 6 | 本次问题的新测试 | 有新增的测试，而且**用真实包**：涉及运行时取数据的，要有"真实目录构建 → 运行时命中"的端到端用例 |

- 测试失败时，先判断是测试过时还是真 bug，**不许为了变绿削弱断言或删测试**。
- 《规矩》里"不许丢的修复"那张表，每条都对应着测试。动到相关代码时，确认对应测试仍然通过。

## 第 5 步：实机验收（人来点，AI 写步骤）

AI 交件时给出测试步骤，要求：
- **短而具体**：选什么皮肤、进哪个界面、看哪一处，以及预期看到什么。
- **每步写清楚预期结果**，出问题时要截图，并写明当时选的是哪个包。
- **改动影响面广时**（例如动了全局挂载、补丁拦截规则），加一轮大范围回归：常用角色皮肤进战斗、几个卡包翻几页、商店、先古遗物/时间线。
- 测完由 AI 读日志核对，确认有没有新报错、预期的日志行有没有出现。

部署测试包：
- **游戏必须先关掉**，再替换 DLL。
- 部署用的构建来自**正式版引用的 Release、`--no-incremental`**，正式版和测试版都能用。
- 旧 DLL 留一份，**只保留最近两版**。

## 第 6 步：提交与交付

- **实机通过后才提交。** 多个已验收的修复可以合成一个提交，但提交说明要逐项列出改了什么、为什么改。
- **版本号：** 没上传工坊时只加第四位；四个文件要同步改（csproj、`Entry.cs`、`SkinChanger.json`、`workshop/workshop.json`）。
- **合并别人的分支：** 在自己最新的 main 上开新分支合并。合并后对照《规矩》里"不许丢的修复"逐条确认，再把第 4 步的门禁完整跑一遍。
- **交接记录**写进 `docs/refactor/`，包括：改了什么（文件和函数）、根因、怎么验证的（哪些测试、实机步骤）、还剩什么没做或没验证。
- 给维护者看的维修日志，用表格写"问题 / 原因 / 修法 / 状态"，状态要区分"实测通过"和"仅离线通过"。

## 多个 AI 同时干活时

- **按独立问题分工，不要按"查"和"修"拆开**：一个人从查到修一条线做完，上下文是连续的。
- **划清文件归属。** 两个人不能同时改同一个文件；SkinService、SkinCatalog 这类核心大文件同一时间只给一个人。实在要并行，就开独立的 git worktree，做完再合。
- 派活时写明要做到什么程度：哪些测试必须过、交接文档写到哪、提交还是不提交、部署还是不部署。

## 交件前核对清单（复制使用）

```
[ ] 根因写清楚了，有证据（文件:行 / 日志行号）
[ ] 只改了相关文件，换行是 LF
[ ] 没有写死游戏路径；没有把原版路径全局改写
[ ] 正式版引用 0 错误 / 测试版引用 0 错误
[ ] LogicTests 通过；完整 RuntimeTests 跑到 "Workshop policy tests passed."
[ ] 动到共享入口或受保护角色：check-protected-characters.ps1 通过
[ ] 新增了用真实包的测试；没有削弱任何已有断言
[ ] 给出实机测试步骤（含预期结果）
[ ] 交接记录写进 docs/refactor/
[ ] 未经实机确认不提交；新增界面文字补齐 15 种语言
```
