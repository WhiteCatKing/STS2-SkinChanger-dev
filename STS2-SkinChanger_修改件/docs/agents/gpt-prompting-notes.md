# 给 GPT 的提示词：少写防御代码、多说人话

> 给白猫：GPT 有两个老毛病。一是**防御性编程**，到处加 try/catch、空值判断、回退分支、开关，代码越改越厚，真 bug 反而被吞掉；二是**不说人话**，满屏英文术语、缩写，还有"X 不代表 Y，更不代表 Z"这种层层叠甲的长句。
> 用法分三层：①放进 `AGENTS.md`，长期生效；②派任务时加一两句；③它又犯了，用一句话纠正。

> 项目内副本：第 ① 节已写进根目录 AGENTS.md（「写代码」「写回复」两节），这里留作说明；第 ②③④ 节供维护者聊天时使用。

## 先看这条：提示词要短，而且要用正面的说法写

社区里有人发现（11-21，未经官方证实，但和我们的经验一致）：GPT-6.2（Astra / Sol）在 Codex 里自带一套新的系统提示词，本身就在压制防御性输出。如果 `AGENTS.md` 里写了大量"不要……""禁止……""要谨慎……"之类的规则，可能和这套内置提示词打架，结果反而更爱叠甲。所以：

- **AGENTS.md 只放必要的东西，越短越好。** 换过以后重启客户端，开新会话再试。改之前先备份旧文件。
- **规则用正面陈述写：直接写"怎么做"，少写"不要做什么"。**
  - 反例："不要为想象中的情况加 try/catch。"
  - 正例："只为日志或复现中出现过的情况写处理分支，并在提交说明里写明对应的日志行。"
- 先用一个小任务对比换之前和换之后的效果，确认确实变好了再长期用。

---

## ① 放进 AGENTS.md（复制整段，已改成正面写法）

```markdown
## 写代码
- 只为实际出现过、或能写出具体触发条件的情况编写处理分支；每个新分支在提交说明里写明对应的日志行或复现步骤。
- 异常在 Harmony 补丁入口统一捕获并记日志；内部逻辑出错时直接抛出，便于定位。
- 修 bug 时直接改对出错的那段逻辑，保持改动行数最少。
- 配置项、开关和抽象层只在维护者提出时添加。
- 复核时只检查交代的要点，按正常玩家的用法判断；其他想法放进末尾的"可选建议"一节。

## 写回复
- 每次回复分两段：
  1. 给维护者看：三句话以内，用会玩这个游戏、但不写代码的人听得懂的话，说明出了什么问题、玩家会看到什么、现在的状态、需要维护者做什么。
  2. 给 AI 看的技术细节：文件、函数、测试名都写在这一段。
- 每句话只说一件事，先说结论再说原因。
- 术语第一次出现时，用半句话说明它是什么。
- 拿不准的地方，写出确认的办法和下一步动作。
```

## ② 派任务时加的话（按需挑一两句）

- **改 bug：** "只修这个问题的根因。改完列出你删了什么、加了什么，每处写一句理由。"
- **怕它加一堆兜底：** "这次的改动只包含修复本身。如果你认为需要额外的处理分支，先停下来给我看它对应哪次实际发生的问题。"
- **复核：** "只看这三点：……。按正常玩家的用法，一遍过。其他想法放进'可选建议'。"
- **要汇报：** "先用三句白话告诉我结果，就像讲给会玩这个游戏、但不懂代码的朋友听，技术细节放在后面。"

## ③ 它又犯了，用一句话纠正

- 满屏术语："用会玩游戏的人听得懂的话重说一遍，三句以内。"
- 代码变厚："逐条列出这次新增的处理分支，并写出每条对应的实际问题；对应不上的删掉。"
- 层层叠甲："只用肯定句，直接说：修好了没有？我要做什么？"

## ④ 换新会话交接时（防止旧会话的叠甲风格带进新会话）

让旧会话写一份交接提示词，要求如下（可以直接复制）：

```
把当前任务的最新状态整理成一份交接提示词，放在一个 Markdown 代码块里，600～1000 字，分四节：
【现场基线】工作目录、分支、基准提交、产物路径、已确认的结果
【目标与验收】下一步目标、已授权直接推进的范围、完成标准
【执行规范】固定的命令和流程、记录哪些内容；常规工作直接做，遇到阻碍或需要决策时再说明
【起手动作】新会话接手后第一步核对什么、然后做什么
全文只用肯定句和明确的动词写操作要求；把踩过的坑直接写成执行步骤或参数；只列下一步必须读的文件。
```

## 关于 ELI5（"像给 5 岁小孩解释"）

可以用，但我更推荐上面这种"讲给会玩游戏、不写代码的人听"：

- ELI5 有时会简化过头，把"哪个皮肤、在哪个界面"这类关键信息也丢掉。维护者需要的是**准确、但不用术语**的说法。
- 把听众设成"会玩这个游戏的人"，GPT 会自然地用卡面、商店、选人界面这些游戏里的词来解释，既听得懂，又不丢信息。
- 临时想让它说得再简单一点，补一句"ELI5"也没问题，当作第 ③ 层的快捷口令。

## 为什么这样写管用

- 要求它**写出对应的实际问题**，等于给了它一把"什么算真问题"的尺子，它自己就会收敛。
- 分两段写，比单纯要求"说人话"更好用：它擅长写技术细节，就照常写，只是先给你一段白话。
- 用正面的说法写规则，它就照着去做；一长串"不要"反而会让它更小心、更爱解释。
